Project Brief for Another LLM
For: Richard Cheam [RC]
Repo: llm-reasoning-mt

1. Project Goal

This project studies why chain-of-thought or reasoning traces help mathematics and coding, but do not seem to help machine translation.

The core research question from the planning document is:
Why does reasoning or CoT help for mathematics and coding, but not for machine translation?

The project is based on the paper "LLM Reasoning for Machine Translation: Synthetic Data Generation over Thinking Tokens".

The repo supports:
- generating reasoning-augmented MT data
- evaluating direct MT and CoT-style MT
- training models with or without reasoning traces
- exporting sentence-level data for later annotation and analysis

2. Richard Cheam [RC] Responsibilities

According to Group_1_2.pdf, RC owns two main parts:

Phase 1:
- tag the dataset
- score each sentence by difficulty
- annotate a subset for linguistic phenomena:
  - ambiguity
  - idioms
  - complex syntax
  - named entities

Phase 2:
- perform trace analysis
- categorize traces into types:
  - correct linguistic analysis
  - hallucinated rules
  - vacuous filler
  - actual translation attempts
  - repetition
- measure overlap between traces and final translations
- analyze trace length vs translation quality
- cross-tabulate with:
  - model
  - language pair
  - prompt type
  - number of shots

This means RC is responsible for the annotation and descriptive analysis layer, not the faithfulness perturbation experiments or the later hypothesis-testing experiments.

3. Important Constraints from Supervisor Feedback

The supervisor raised a contamination concern.

Operational rules:
- do not generate reasoning traces on held-out test sets such as FLORES devtest if those sets are meant for evaluation
- if an LLM is used for difficulty tagging, pass only the source sentence
- do not give the LLM:
  - reference translation
  - model translation
  - reasoning trace
- keep the tagging prompt fixed across batches
- keep the tagging settings fixed across batches
- add a small manual audit sample for consistency

Safe interpretation:
- sentence difficulty tagging should be source-only
- trace analysis should be performed only on traces already collected from allowed non-test settings, or on evaluation outputs that are explicitly part of the analysis design and not reused for model selection or prompt tuning

Reproducibility interpretation:
- if LLMs are used for annotation, the annotation setup must be frozen and documented
- do not rely on an interactive proprietary assistant such as Claude Code or ChatGPT as the final annotation mechanism
- instead, use a reproducible scripted pipeline with:
  - a fixed model name
  - a fixed model revision or checkpoint
  - a fixed prompt template
  - fixed decoding settings
  - fixed codebook
  - saved raw outputs
  - saved parsed labels
- if possible, prefer a Hugging Face model with a versioned checkpoint so another person can rerun the same annotation process

6. Annotation Schema RC Should Use

The annotation scheme that has already been stabilized in discussion is:

difficulty_score:
- 1 trivial
- 2 easy
- 3 moderate
- 4 difficult
- 5 very difficult

Difficulty is based only on the source sentence.

Linguistic phenomena:
- ambiguity
- idiom
- complex_syntax
- named_entities
- figurative_language
- long_distance_dependency

Trace type labels:
- CORRECT_LINGUISTIC_ANALYSIS
- HALLUCINATED_RULE
- VACUOUS_FILLER
- TRANSLATION_ATTEMPT
- REPETITION

Trace metrics:
- trace_length_estimate
- trace_translation_overlap
- trace_usefulness

Expected qualitative output per example:
- a structured JSON object with deterministic fields

Recommended naming for the method:
- "LLM-assisted annotation" is the safest and most accurate umbrella term
- if the model assigns labels using an explicit rubric or codebook, call it:
  - "rubric-guided LLM annotation"
  - or "codebook-guided LLM annotation"
- "LLM-as-a-judge" is better reserved for cases where the model evaluates or scores an output against a criterion
- for this project, a good formal description is:
  - "codebook-guided LLM-assisted annotation with manual audit"

7. RC Workflow Recommendation

Step 1:
Build or collect a clean analysis table with one row per example.

Minimum columns:
- source_sentence
- reference_translation
- model_translation
- reasoning_trace
- model_name
- language_pair
- prompt_type
- number_of_shots
- decoding_temperature
- evaluation scores if available

Step 2:
Create a deterministic annotation codebook.

This should define:
- how to assign each difficulty score
- what counts as ambiguity
- what counts as complex syntax
- when a trace is vacuous filler vs correct linguistic analysis
- how to assign overlap and usefulness consistently

This codebook should be treated as part of the method, not just as notes.
It should be versioned and cited in the report.

Step 3:
Run a small pilot annotation pass.

Recommended:
- 50 to 100 examples

Purpose:
- refine the codebook
- identify ambiguous edge cases
- make future labeling more consistent

Step 4:
Annotate the full RC subset.

Recommended sampling:
- stratify by model
- stratify by prompt type
- stratify by language pair
- stratify by number of shots
- include both strong and weak translations
- include both short and long traces

If using LLM-assisted annotation, log for each batch:
- annotation model name
- Hugging Face repo id
- revision or commit hash if available
- prompt template version
- codebook version
- decoding settings
- date of run

Step 5:
Produce descriptive Phase 2 analysis tables.

Examples:
- trace type by prompt type
- trace type by model
- trace usefulness by quality bucket
- overlap vs translation quality
- trace length vs translation quality

8. Concrete Analyses RC Should Prioritize

A. Sentence difficulty tagging
- assign difficulty_score from source sentence only
- write short deterministic justification

B. Linguistic phenomena tagging
- annotate a subset for:
  - ambiguity
  - idiom
  - complex syntax
  - named entities
  - figurative language
  - long-distance dependency

C. Trace categorization
- dominant trace type
- all secondary trace types

D. Trace usefulness analysis
- helpful
- neutral
- harmful

E. Trace overlap analysis
- none
- low
- medium
- high

F. Descriptive correlation analysis
- does longer trace correlate with better translation?
- do translation attempts correlate with better quality?
- are vacuous traces common in poor translations?
- are correct linguistic analyses rare or common?

9. Reproducibility Protocol For RC

If RC uses an LLM to accelerate annotation, the process should be reproducible.

Minimum reproducibility requirements:
- use a fixed Hugging Face model rather than an opaque interactive assistant
- save the exact prompt template used for annotation
- save the exact codebook used for annotation
- use deterministic decoding whenever possible:
  - temperature 0.0
  - greedy decoding if supported
- save the raw model response before parsing
- save the parsed JSON label output
- keep a manual audit subset for quality control

Recommended artifacts:
- `annotation_codebook_v1.md`
- `annotation_prompt_v1.txt`
- `annotated_batch_v1.jsonl`
- `annotation_metadata_v1.json`

Suggested metadata fields:
- annotation_model_name
- annotation_model_revision
- annotation_prompt_version
- annotation_codebook_version
- annotation_date
- annotation_temperature
- annotation_parser_version

If you use a proprietary API model for exploratory work, treat that only as pilot work.
For the final reported method, switch to a documented, rerunnable pipeline.

11. What Another LLM Should Do If Asked To Continue RC Work

If another LLM continues this work, it should:
- preserve contamination controls
- preserve reproducibility constraints
- avoid changing the annotation schema unless clearly justified
- keep labels deterministic across batches
- prioritize building reusable annotation tables and codebooks
- focus on RC-owned tasks:
  - difficulty tagging
  - linguistic-phenomena annotation
  - trace categorization
  - overlap/usefulness analysis
- not spend time on large new modeling experiments unless explicitly requested
